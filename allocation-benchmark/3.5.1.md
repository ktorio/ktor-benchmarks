## Allocation Benchmark Results: 3.5.0 → 3.5.1

> ⚠️ This report was generated with AI assistance and may contain incorrect attributions or false claims. Please verify before publishing.

### Key Takeaways

**Improvements**

- None identified. The apparent Java and OkHttp client improvements are dominated by suspension-count and pooled-segment churn, so they are treated as measurement artifacts.

**Regressions**

- **Immediate cancellation propagation slightly redistributes CIO response allocations: gzip and streaming responses allocate about 1 KB more, while file responses allocate 955 bytes less.**
  [KTOR-9629 / #5588](https://github.com/ktorio/ktor/pull/5588) — `ByteChannel.attachJob` now reacts while its job is cancelling instead of waiting for completion. Call-site analysis shows more consumer-side `ByteChannel.awaitContent` continuations, offset by fewer `CIOReader` and selector suspensions. Two independent 3.5.1 runs reproduced the scenario totals within 222 bytes.

**Measurement artifacts**

- **OkHttp streaming appears to improve by 272,060 bytes (7.5%), but this is the documented scheduler-dependent segment-pool variance rather than a confirmed improvement.**
  The change is dominated by 8 KiB arrays under `OkHttpEngine.toChannel` and remains within the configured 278,528-byte known-variance bound.

- **The Java streaming/compressed decreases and OkHttp gzip increase mostly reverse the `ByteChannel` swings recorded in 3.5.0.**
  Call-site analysis attributes them to different `awaitContent` suspension counts and segment-pool timing rather than source changes in those engine paths.
