## Allocation Benchmark Results: 3.4.3 → 3.5.0

> ⚠️ This report was generated with AI assistance and may contain incorrect attributions or false claims. Please verify before publishing.

### Key Takeaways

**Improvements**

- None identified. The apparent client streaming/gzip improvements are dominated by pooled segment and suspension-count churn, so they are treated as measurement artifacts.

**Regressions**

- **Jetty file responses allocate ~648 bytes more in the response writer path.**
  [#5607](https://github.com/ktorio/ktor/pull/5607) — the Jetty 12.0.29 → 12.0.35 update adds `org.eclipse.jetty.util.thread.Invocable$ReadyTask` allocations under `JettyResponseBodyWriter`; Ktor's Jetty writer code did not change.

**Measurement artifacts**

- **Static file responses show +632 bytes across all server engines because the benchmark runtime classpath grew.**
  [KTOR-9542 / KTOR-9531 / #5602](https://github.com/ktorio/ktor/pull/5602) adds `io.netty:netty-codec` to `ktor-server-netty`; because the allocation benchmark runs with all server engines on one test classpath, `ClassLoader.getResources()` in `StaticContentResolution` scans a few more jars even for CIO/Tomcat/Jetty.

- **OkHttp streaming response is flaky by ~270 KB between runs, so the TeamCity +267,633 bytes (+7.9%) is not a confirmed regression.**
  The TeamCity dump is dominated by extra 8 KB `[B` arrays under `OkHttpEngine.toChannel`; a local rerun against the same 3.5.0 baseline reversed the result by −272,247 bytes, with `OkHttpEngine.kt` alone decreasing by −263,327 bytes.

- **Client streaming/compressed `ByteChannel` swings are mostly pooled segment and coroutine suspension-count churn.**
  The CIO streaming decrease, Java compressed/streaming increases, and smaller OkHttp gzip decrease are dominated by 8 KB segment arrays plus `ByteChannel.awaitContent` continuations; these depend on segment-pool hit rate and scheduler timing.
